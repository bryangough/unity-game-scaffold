# The method: from an idea to a game on a store

How three small games got made by one person who plays and decides and one assistant who builds and verifies. None
of it needs an assistant; all of it assumes the two roles are kept apart.

## 1. Ideas go into one throwaway project

Keep one Unity project that never ships (the *idea test bed*). Every idea gets a folder, `Proto_NN_Name/`, with
`Scripts/`, `Editor/NameSceneBuilder.cs` and nothing else; the scene is generated by the builder. The shared kit
(`FunTestKit`, `GameFeel`, `TouchInputAdapter`, `PrototypeUIHelper`) lives in `Common/` and is used, not copied.
A launcher (Tab) hops between scenes; one batch menu rebuilds every scene, so one compile error anywhere is found at
once (it blocks every scene, so compile health is always task zero).

The job of a prototype is **not** to build the game in the design doc. It is a **two-minute playable** that answers
one question: *is the core verb fun enough to deserve its own project?* The scope is fixed: input → the core verb →
feedback → **a win and a lose both reachable inside 120 s** → restart. Primitives only; no art, audio or features
before the verdict. The brief for each is one table row (idea, inspirations, the verb, why this order), and the
cheapest verdict is built first.

Each prototype's task section has: the **fun question**, what the **audit** found, three or four tasks, and a
**Try:** line that says what the owner should feel. The owner plays each one for ten minutes with a mouse and writes
a line in `PLAYTEST_NOTES.md`; the assistant adds only the "Built:" line. The scoring rule that worked: *18+ graduate
· 12–17 one change then retry · under 12 park with a one-line reason*. In practice the owner's words decided it before
a score ("liking more", "prep for its own game", "love it, get it into its own folder").

Rules that emerged from the test bed and carried into every game:
- new twists only every ~10 levels; base rules first;
- "pick-up-and-play, like an older Flash game": one tap to play, one board, a few minutes a game, nothing to sign in to;
- fix the feel before adding anything.

## 2. A winner graduates

A graduate gets its own project **made from this scaffold** (`tools/new_game.py`), and is **removed from the test
bed** once copied, so work on it happens in one place. `tools/graduate.py` moves the scripts into the game's
assemblies and namespace, and writes `Assets/docs/initial/fun_test_record.md`: the test bed's task row (how it was
built), the owner's playtest lines, and the design doc. That record is kept for the life of the game as "where this
came from"; the plan lives in `TASKS.md`.

Graduation changes the rules: Input System only (the test bed tolerated legacy keys), portrait, a save, a phased
plan. The first commits are housekeeping: own the code (`Assets/Game/`, a namespace, a menu), the scene from
the builder, the current level surviving `R`.

## 3. The plan is one file

`Assets/docs/TASKS.md` is the only list of open work (see [`tasks_guide.md`](tasks_guide.md)). It opens with
*where the game is* in two sentences, the **ground rules**, and **the bar** every task is judged against. Then
*Next up* (the assistant's order), *Waiting on the owner* (their list: things to play, to hear, to decide, accounts
to make), and the **road to a full game**: six milestones, each with the owner's check in plain words:

| | Milestone | The owner's check |
|---|---|---|
| M1 | Ten levels prove the base | plays ten and says "we have a game" |
| M2 | In a hand | ten inputs on a phone without one going wrong; reads at arm's length |
| M3 | A game around the levels | a new player gets from the icon to level 3 with nobody explaining anything |
| M4 | A look and a sound | nothing on screen is a grey box; sounds approved by ear; the phone frame holds |
| M5 | Forty+ levels | play 1 → N; each chapter teaches its twist in its first level without text |
| M6 | Released | live on itch.io, Play internal testing and TestFlight; three friends finish ten levels unaided |

The phases below the table hold the briefs (0 own the code · 1 the base game · 2 phone and web builds · 3 rules ·
4 look and sound · 5 the game around the levels · 6 store and release · 7 cleanup). The template in this scaffold
has the briefs every game needed; a game deletes what it does not and adds its own.

## 4. How a task runs

1. The assistant takes the top of *Next up* (fixes before content, unless the owner asks for content).
2. It builds it the way the conventions say: rules in plain C# with a test, the scene from the builder, levels as
   data, every input an action, primitives until the art pick.
3. It verifies before hand-off: compile clean (read `Editor.log`), scene rebuilt from its menu, tests green, the
   level check and the replay clean, the changed levels played to a win and a loss, `R` restarts.
4. It writes the *Done* line under the task: the date, what was built, the numbers chosen and why, what was **not**
   verified (e.g. "not play-tested by the assistant"). Then one commit: `type(phaseN): summary`.
5. The owner plays the *Try:* line and answers in a few words. Those words go into the task list verbatim, with the
   date, as a decision or a new task. Terse answers are fine; the assistant recommends one option per question.

## 5. Checks that run from a menu

Every game grew a set of one-click checks, each writing a Markdown report into `Builds/Checks/` so the result can
be read later (by the owner, by the next session, by a commit message):

- **Validate levels**: every level winnable at its par, needs its rule, reads at a glance, starts safe. Cached per
  level by a hash of the level and the rules' source, so only changed levels are re-solved.
- **Replay**: every level's solution played through the real game, a key per beat, one tick a frame; a level the
  solver wins but the game does not means the views, the input or the frame loop disagree with the rules.
- **Tests**: EditMode, through the Test Runner API to a report (the MCP cannot open the window).
- **Size**: every build writes the packed assets by kind and the 25 heaviest; the web download is logged against a
  budget. Cuts are picked by size, not guessed.
- **Sound report**: what the clips cost in git and in a phone build.
- **Colour check** and **smoke run**: a capture under five kinds of vision; the game opened, drawn and restarted by a
  bot with no hand on it.
- **Keys and pad**: the menus played through on a keyboard and a virtual pad.

## 5b. Content as scripts, themes as data

The duel game (two full themes on one rules core) added two habits the others kept in smaller form:

- **Every prefab, asset and data table is made by an editor script**, re-runnable, named after the plan's phase
  (`Phase4Setup`, `Phase4FArenasSetup`...), run in a documented order. Nothing is hand-placed; a rebuild is a menu
  click; the plan's ids are in the code. The scaffold's `SceneBuilder` is the first of these; a game adds more as
  it grows (a theme builder, a level-select builder, a store-art builder).
- **Theme is data, rules never read it.** Words, sprites, prefabs, clips and sounds come through one theme asset;
  the rules core sees none of it, and a build strips the inactive theme. That is what let a reskin ship without
  touching a rule, and what lets a 2.0 add new tile sets to a finished game.

## 6. Assets

The owner's packs live on a shelf outside every project (one folder shared by every project). Nothing is imported until
the **art pick**, made from screenshots; then only the subset a builder uses is copied in (follow GUID dependencies,
never overwrite), and a **theme asset** dresses the primitives so a level never references a model. Sound libraries
are never dropped into `Assets/`: a picks list names the files (two to four variants per sound, so the owner hears
candidates in play), an import menu copies them in with mobile import settings and builds the bank. Music comes in
as calm / full stems, downsampled on the way in, and ships packed in per-track bundles that stream on demand: out of
the first web download, and never a loose file on a server (most music licences forbid that).

`Store/licences.md` lists every source that ships and its licence before release; a pack with no licence to read is
removed. The repo stays private while bought packs are in it.

## 7. Release

Web first: the itch.io build doubles as the phone test (`Serve Web Build on the LAN`, then the zip). Then Google
Play (an upload key made once by the tool and kept outside the repo; a signed bundle; internal testing), then the
App Store (an Xcode project archived on a Mac; TestFlight). The store text, the privacy policy ("nothing collected";
the Android app asks for vibration only) and the screenshots (captured in Play mode, posed by level title) are
tasks like any other. Version 1.0 is a tag and a release run: a fresh install reaches level 1 in one tap, every
level passes the check and the replay, progress survives an update. Then a friends test: three people who have never
seen it, ten levels, nobody helping.
